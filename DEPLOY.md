# Deploying to Render (free)

This deploys three things on Render's **free** tier from one repo:

| Component | Render service type | Public? |
|---|---|---|
| PostgreSQL database | Managed Postgres | no (internal) |
| Django REST API | Web Service (Python) | yes |
| React frontend | Static Site | yes ← **testers open this** |

Everything is described in [`render.yaml`](./render.yaml), so Render provisions it
all in one shot as a **Blueprint**.

> **Free-tier caveats (important, but fine for testing):**
> - The API **sleeps after ~15 min idle** and takes ~50s to wake on the next
>   request. The first click after a quiet period is slow; after that it's fast.
> - The **free Postgres database is time-limited** (Render currently expires free
>   databases after ~30 days). Note the expiry date Render shows you; when it
>   lapses, create a new free DB and redeploy.
> - Render's disk is ephemeral, which is exactly why documents are **not** stored
>   on it: every upload goes to a private S3-compatible bucket (Step 1a) and is
>   read back through short-lived presigned URLs.

## Step 1a — Create the private storage bucket (once)

Every uploaded document — Aadhaar, PAN, Safety certificate, Medical, PVC and
Resume — is stored in one **private** S3-compatible bucket. Supabase Storage is
the reference option (free tier, S3-compatible endpoint):

1. Create a project at <https://supabase.com>.
2. **Storage** → **New bucket** → name it `gate-intake-docs` and leave **Public
   bucket OFF**. This is load-bearing: the app never mints public URLs, only
   presigned ones.
3. **Project Settings → Storage → S3 access keys** → **New access key**. Copy the
   access key id and secret — the secret is shown once.
4. Note your endpoint and region:
   - `S3_ENDPOINT_URL` = `https://<project-ref>.storage.supabase.co/storage/v1/s3`
   - `S3_REGION` = the project's real region, e.g. `ap-south-1`
     (Supabase rejects `auto`; only Cloudflare R2 accepts it)

Cloudflare R2 and MinIO work identically — same client, different endpoint.

> Skipping this step is survivable for a demo: with `S3_ENDPOINT_URL` empty the
> app falls back to signed local files, but Render's ephemeral disk means those
> uploads vanish on restart.

## Step 1 — Create the Blueprint on Render

1. Sign in at <https://dashboard.render.com> (free account, no card needed for
   free services).
2. **New +** → **Blueprint**.
3. Connect your GitHub and pick the `factory-gate-intake` repo.
4. Render reads `render.yaml` and shows a plan:
   - `gate-intake-db` (Postgres, free)
   - `gate-intake-api` (web service, free)
   - `gate-intake-web` (static site, free)
5. Render prompts for the values marked `sync: false` in `render.yaml` — paste
   the three storage credentials from Step 1a (`S3_ENDPOINT_URL`,
   `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`). Leave `ANTHROPIC_API_KEY` /
   `GEMINI_API_KEY` blank unless you are switching the resume parser off the
   default keyless `ocr` provider.
6. Click **Apply**. Render provisions the DB, then builds the API and frontend.

`PII_ENCRYPTION_KEY` and `PII_BLIND_INDEX_KEY` are generated by Render and must
then be left alone: rotating the first makes stored candidate names, phones and
emails unrecoverable, and rotating the second breaks name search and duplicate
detection for existing rows.

The API's `startCommand` runs `migrate` + `seed_data` automatically, so the dummy
personas and sample data are created on first boot. Migration `0007` installs the
`pgcrypto` and `pg_trgm` extensions plus the `app_encrypt` / `app_decrypt` /
`app_blind_index` helpers — Render's managed Postgres grants the app user rights
to do this. If your database does not, run
`CREATE EXTENSION pgcrypto; CREATE EXTENSION pg_trgm;` once as an admin and
redeploy; every statement in that migration is `IF NOT EXISTS`.

## Step 2 — Confirm the URLs (one-time)

`render.yaml` assumes these hostnames:

- API → `https://gate-intake-api.onrender.com`
- Web → `https://gate-intake-web.onrender.com`

If those service names were globally taken, Render appends a random suffix. Check
each service's real URL in the dashboard. **If either differs from the above:**

1. On **gate-intake-api** → *Environment* → set
   `CORS_ALLOWED_ORIGINS` to the real frontend URL.
2. On **gate-intake-web** → *Environment* → set
   `VITE_API_BASE_URL` to the real API URL **+ `/api`**.
3. Redeploy the affected service (frontend must rebuild since the API URL is baked
   into the bundle at build time).

If the names came through as-is, no changes are needed.

## Step 3 — Smoke-test

1. Open the **frontend URL**. (First load may take ~50s while the API wakes.)
2. It should land on the Principal Employer dashboard.
3. Use the header **role-switcher** to move between the three personas — no login
   needed, they're seeded.
4. Quick end-to-end check:
   - **Contractor** → *Workforce Demand* → type `3` / `Carpenter` → **Search my
     pool**; you should see availability and shortfall.
   - **Contractor** → *Worker Pool* → project *Plant-A* → *Fix Requirements*
     shows gaps; submit a list.
   - **Contractor** → **＋ New Worker Intake** → attach any PDF to a slot and
     confirm the document lands (check *Verification Status* → 📎 opens a signed
     link).
   - **Principal Employer** → approve the list.
   - **Gate Security** → enter `100000000001` → **GREEN**; `100000000005` → **RED**.
5. Real-time gate check: in the Django admin (`/admin`), edit Ravi Kumar's
   medical record and set `exam_date` more than a year ago. Re-scan
   `100000000001` at the gate — it must now flash **RED — DOCUMENT EXPIRED**
   despite the list still being approved.

## Re-seeding / resetting data

Data resets are safe to trigger by redeploying the API (seed is idempotent). To
wipe and repopulate from scratch, delete + recreate the `gate-intake-db` database
in the Render dashboard, then redeploy the API.

## Troubleshooting

| Symptom | Fix |
|---|---|
| Frontend loads but every action errors / CORS error in console | `VITE_API_BASE_URL` (frontend) or `CORS_ALLOWED_ORIGINS` (API) doesn't match the real URLs — see Step 2. |
| `DisallowedHost` in API logs | Add the host to `DJANGO_ALLOWED_HOSTS`; `.onrender.com` should already cover it. |
| First request very slow | Expected — free web service was asleep. Subsequent requests are fast. |
| API build fails on `psycopg2` | Ensure `PYTHON_VERSION=3.12.6` is set (it is, in `render.yaml`). |
| DB connection refused after a few weeks | Free Postgres expired — create a new free DB, point `DATABASE_URL` at it, redeploy. |
| `permission denied to create extension "pgcrypto"` | Run `CREATE EXTENSION pgcrypto; CREATE EXTENSION pg_trgm;` as a DB admin once, then redeploy. |
| Document links 404 or "SignatureDoesNotMatch" | `S3_REGION` must be the bucket's real region — Supabase rejects `auto`. Check it matches the project region. |
| Uploads succeed but files vanish after a restart | `S3_ENDPOINT_URL` is empty, so the local fallback is in use on Render's ephemeral disk. Complete Step 1a. |
| Candidate names show as `—` after a key change | `PII_ENCRYPTION_KEY` was rotated; the old ciphertext is unreadable. Restore the previous key. |
